## Changes and Responsibility

- Existing writer/reviewer tasks compare the participation relationship,
  responsible object and scope, rather than absence of one modifier.
  Editorial uncertainty may be observed only when all substantive checks are
  affirmative; uncertainty about significant facts remains a failure.
- Summary consumes the already supplied frozen actions and confirmed background
  declarations. Forced value-result structures exit Canonical tasks; no second
  evidence compilation or deterministic summary generator is introduced.
- After explicit scope approval, professionalization leaves accepted Canonical
  summary semantics untouched. Legacy derivations remain available; existing
  safety and format checks remain active. Project receipts do not certify
  arbitrary global summary semantics.
- Skill taxonomy compacts prefixes only for qualified items with the identical
  original declaration span and identical degree wording. Distinct declarations,
  degrees, conflicting qualifications and scope-bearing clauses are retained.
  Existing Token relevance handling remains independently addressable. This is
  display-only: aggregation, eligibility and source records do not change.
- ResultPage presents bold plus boundary, copies the persisted bold string and
  preserves paragraphs instead of reclassifying later sentences as reminders.
  Boundary risk labeling is separate from model content. Unknown deployment
  status is not a confirmed negative merely because classroom demonstration is
  known. Boundary text never becomes project evidence.

The single formal model writer remains the only producer of substantive project
and summary expression. Reviewer returns judgments only. Receiver derives
attachments; downstream cannot use valid IDs to expand responsibility. Facts,
Claims, owners, eligibility, Authority, Ledger and existing refusal exits remain
unchanged. v2 composition and v6 review formats and three-call total budget are
unchanged. Major uncertainty is not uniformly waived.

## Compatibility and Delivery

The four API fields remain populated and stored; normal/recommended are hidden
in the current version chooser, not deleted. No schema, database migration or
historical result rewrite occurred. New accepted Canonical results still map
bold from actual final structured sections before final Gate and use the same
revision for DOCX. Older stored results may retain the old independent bold
string and are not retroactively claimed to match DOCX. Resume preview still
shows only the first project and the first three detail rows.

Summary, skills and compatibility versions do not gain project-level semantic
receipts. Summary may still contain model-origin unsupported generalization;
existing global safety checks are not a complete semantic proof. A thin resume does
not authorize adding concrete work, achievements or seniority.

Engineering acceptance is complete; competitive-packaging publication
acceptance is not. Remaining observed limitations:

- Saved project text largely retains original/first-person wording, repeated
  header dates and weak organization. A saved original sentence is not evidence
  of packaging improvement.
- Normal summary introduces an independent-capability phrase without the
  project-level semantic review; accepted project receipts do not certify it.
- Boundary wording can overstate unknown status or team size and still refer
  users to hidden normal/recommended versions. It is not formal project
  evidence and has not obtained equivalent semantic proof.
- An existing boundary professionalization branch turns the complete reminder
  `面试前建议补充` into `面试前` and collapses paragraphs; other saved boundaries
  contain doubled punctuation. Stage snapshots place the first reminder change
  in professionalization, not in the model return. Only the summary branch was
  approved for adjustment, so this separate defect was recorded, not expanded
  into an unapproved fix.

No deployment is recommended from these results. Further implementation needs
separate approval; more calls alone do not resolve the observed quality gaps.

skill-display switch and two-version UI mapping. Preserve v0.9.19.5/6 budgeting,
source validation, receipts, Gate and stored revisions. No data rollback is
needed. Do not restore unsafe summary derivation or weaken failures just to
match old snapshots. No deployment, commit or push has been performed.
