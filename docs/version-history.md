# 版本历史

## v0.4.4：Experience Fact Ledger 与事实覆盖

- 将经历边界从项目级进一步下沉到原子事实级，为每条明确事实生成内部 `fact_id`。
- 新增事实覆盖率检查和高价值事实恢复，避免长而充实的输入在生成过程中被过度摘要。
- 清除项目详情中的通用填充句，并阻止其他 experience_id 的事实进入当前项目。
- 详情预算改为高价值事实优先，在两页简历预算内优先保留技术、工程实践、证据和量化结果。

## v0.4.3：经历类型校准与正文完整性

- 以 `source_experience_id` 对应的原始经历类型校准项目 `meta`，阻止全局“实习”信息污染个人项目。
- 调整正式简历分组优先级，在技能与能力之后优先展示真实实习经历。
- 将内部检索摘要与正式简历正文隔离，避免裁剪预览污染模型输出。
- 新增正文完整性检查与结构化日志，可恢复或安全清理被截断的简历语句。

这份记录用于阶段性收口复盘，也可以作为后续项目展示、简历项目经历和产品迭代总结的素材。

## v0.0：核心链路起点

v0.0 完成了 Resume Coach App 的最小可运行闭环。系统支持用户输入经历，由后端生成结构化结果，前端展示包装版本、Claim 风险、面试追问和知识补齐清单，并支持生成 DOCX 文件下载。

这一阶段重点不是生成质量，而是验证产品主链路是否成立：输入经历、生成结果、查看建议、导出简历、提交反馈、记录埋点。

主要能力：

- 初始化 React + TypeScript + Vite + Ant Design 前端。
- 初始化 FastAPI + SQLite + SQLAlchemy 后端。
- 建立匿名用户、会话、事件、输入、生成结果、Claim、简历版本、生成文件和反馈表。
- 实现 mock 生成服务。
- 实现 DOCX 生成与下载。
- 实现基础埋点和反馈。

## v0.3.0：多段经历输出质量优化

v0.3.0 从“稳定性收口”进入“输出质量优化”。这一版重点解决长输入、多段经历场景下模型过度摘要的问题：用户输入越丰富，结果不应该越短，也不应该把多个项目随意合并成一个泛泛的“综合经历”。

主要能力：

- Prompt 增加多段经历识别规则，要求模型先判断用户输入中的主要经历数量。
- 多个项目、实习、开源、比赛经历应尽量分别进入 `resume_sections.projects` 或相关简历模块。
- 增加输出密度规则：单段经历保留 4-6 条细节，两段经历每段 4-5 条，三段经历每段 3-4 条。
- 明确长输入不应被压缩到每段只有 1-2 条，除非经历高度重复或信息极少。
- Fallback 支持从 `recommended_version` / `bold_version` 中解析多个项目段落，识别“项目一 / 项目二 / 经历一 / 开源经历 / 实习经历 / 比赛经历”等分段。
- 结果清洗层放宽项目、Claim、面试计划和知识清单数量上限，避免稳定性裁剪反过来伤害内容完整度。
- DOCX 导出支持最多两页内容承载，优先保留关键项目经历和技术细节，而不是强行压缩成一页。
- 继续坚持事实边界：可以大胆包装职责表达，但不凭空增加用户没有提供的硬事实。

这一版的核心原则是：

> 输入越丰富，输出应该更完整，而不是更短。

## v0.3.1：长输入抗失败修复

v0.3.1 针对真实长经历输入继续修复。真实用户并不会总是按“项目名称：”“项目简介：”这样的标准字段填写，而是更常使用“项目一｜AI RAG 智能助手”“### 项目二｜Resume Positioning Coach”这样的自然标题。如果系统只识别标准字段，就会在长输入时出现无法生成、项目被合并或细节被稀释的问题。

主要能力：

- 新增经历分段预解析服务，在调用 LLM 前识别主要经历数量、标题和摘要。
- Prompt 中加入“系统预解析经历”，帮助模型在长输入中保持项目边界。
- Fallback 支持中文冒号、英文冒号、竖线、全角竖线、短横线和破折号等标题分隔符。
- 对长段落增加逗号级细节拆分，避免一个项目只有 1-2 条 details。
- 默认 LLM 超时从 30 秒提高到 60 秒，默认输出上限从 4096 tokens 提高到 8192 tokens，降低长输出被截断导致 JSON 解析失败的概率。
- 新增真实长输入风格测试，覆盖“项目一｜标题 + Markdown 二级标题”的输入形式。

这一版的重点不是鼓励灌水，而是避免模型因为输入变长而丢掉用户已经提供的事实和技术细节。

## v0.3.2：事实防幻觉与包装增益

v0.3.2 处理输出质量的另一个核心矛盾：既不能编造硬事实，也不能把用户输入原样复述一遍。真实用户反馈中出现过两类问题：一是用户没有提供专业，结果却暗示“计算机相关专业”或“科班背景”；二是用户输入很完整时，模型只是做关键词提取，用户感觉“和我说的没什么区别”。

主要能力：

- 新增 `fact_guard_service.py`，用于清理硬事实幻觉。
- 对教育经历中未提供的学校、专业、学历、时间强制保留 `[待填写]`。
- 对“计算机相关专业”“科班背景”“企业级生产系统”“高并发”“模型训练经验”等隐性硬事实进行降级。
- 新增 `enhancement_guard_service.py`，用于检查推荐版本和项目细节是否过度接近用户原文。
- 对“写页面 / 调接口 / 修 bug / 写文档 / 做 RAG”等软事实进行更正式的职责和技术动作表达。
- 生成链路调整为：结果清洗 -> 硬事实守卫 -> 简历结构兜底 -> 包装增益守卫 -> 再次硬事实守卫。
- DOCX 导出前也会执行硬事实守卫和包装增益检查，历史结果重新导出时也能降低幻觉风险。

这一版的核心原则是：

> 硬事实不能编造，软事实必须增益。

## v0.3.3：非项目经历覆盖增强

v0.3.3 解决另一个真实简历场景问题：用户输入的不一定都是项目经历，还可能包含实习、科研、竞赛、开源、校园 / 社团等经历。如果系统只围绕项目经历优化，这些内容容易被合并、摘要，甚至没有进入最终 DOCX。

主要能力：

- 不改数据库 schema，不改后端 API schema，继续复用 `resume_sections.projects` 作为统一经历承载结构。
- 通过 `project.meta` 区分不同经历类型，包括项目经历、实习经历、科研经历、竞赛经历、开源经历、校园 / 社团经历。
- 分段识别支持“实习经历”“科研经历”“研究经历”“论文经历”“竞赛经历”“比赛经历”“社团经历”“志愿经历”等标题。
- Fallback 支持从原始输入中补回 LLM 漏掉的非项目经历，不再只在 projects 为空时才兜底。
- DOCX 从单一“项目 / 实习 / 科研 / 竞赛经历”总标题改为按类型分组的小标题，例如“项目经历”“科研经历”“实习经历”“竞赛获奖”。
- fact guard 保留用户真实提供的实习经历，不会把真实实习误判为企业级幻觉。

这一版的核心原则是：

> 简历不是只有项目经历，用户给出的重要经历都应该被看见。

## v0.3.4：长输入低 token 稳定生成

v0.3.4 继续处理长输入场景，但重点从“多段经历不丢失”推进到“更低成本、更快响应、更少失败”。真实长输入会同时拉高输入 token 和输出 token：原文很长，完整 prompt 很长，最终还要生成三档包装、Claim、面试准备和 `resume_sections`。这会带来响应慢、成本高、JSON 截断、API 超时和无法生成等问题。

这一版的核心设计是：

> 长输入先本地压缩，再用短 prompt 生成核心结构；模型失败时，用户仍能拿到基于原文的稳定结果。

主要能力：

- 新增 `long_input_service.py`，根据原文长度、行数和经历段数判断是否进入长输入模式。
- 本地预处理长输入，提取每段经历的类型、标题、摘要、技术词、证据词和风险词，形成 `compact_experience_context`。
- 新增长输入短 prompt：`prompts/generate_resume_coach_result_long.md`，减少冗长规则和输出规模，优先保证 `resume_sections.projects` 完整。
- `prompt_service` 支持根据 `long_input_mode` 自动选择普通 prompt 或长输入短 prompt。
- 增强 JSON 修复：对疑似截断的 JSON 尝试补齐括号和方括号，失败后交给稳定兜底。
- 新增 `stable_generation_fallback_service.py`，在 LLM 调用失败、JSON 修复失败或 schema 校验失败时，基于本地分段生成保底 `GenerationPayload`。
- fallback 不调用 LLM，不编造学校、专业、公司、用户数、star、并发、奖项、模型训练等硬事实。
- 新增 `generation_stability.jsonl`，记录长输入模式、prompt 类型、LLM 成功状态、是否触发 fallback、耗时和错误信息。

这一版的产品意义是：用户输入越长，系统不应该变得更脆弱。即使上游模型偶发失败，前端也不应该直接崩掉；但开发者可以通过稳定性日志发现失败和成本问题。

## v0.3.5：经历边界与自然承接知识

v0.3.5 进一步修复长输入多经历场景下的输出质量问题。真实用户输入多个项目、实习或竞赛经历后，模型有时会把 A 经历的技术、部署、用户数或成果写到 B 经历里，造成事实串通；同时，模型也可能把“Docker（如有）”“LangGraph（建议掌握）”这类不确定表达直接放进简历主体，影响专业度。

这一版的核心原则是：

> 一段经历只能使用自己的事实；自然承接知识可以写，但必须能被面试准备接住。

主要能力：

- 在长输入预处理中为每段经历生成内部 `experience_id`，例如 `EXP-001`、`EXP-002`，用于 prompt 和后端守卫，不暴露给用户。
- compact context 明确列出每段经历自己的技术词、证据词、风险词和可自然承接知识，提示模型不得跨 experience_id 借用事实。
- 新增 supported inference：基于规则识别自然承接知识。例如 RAG / 检索 / 测试集可以承接 Top-K、Retrieval、Chunk、Embedding、Recall、Groundedness 等；接口联调可以承接 RESTful API、参数校验、异常处理；部署经历可以承接反向代理、进程守护和健康检查。
- 新增 experience boundary guard：生成后再次检查项目是否继承了其他经历的技术、指标、部署或成果，发现串通则删除或降级。
- 新增 uncertain expression cleanup：清理简历主体中的“如有 / 可补充 / 建议掌握 / 待补充”等不确定口吻，并将对应知识转入面试准备或知识清单。
- DOCX 导出前也执行边界检查和不确定表达清理，历史结果重新导出时同样受保护。

这一版让系统从“能承载多段经历”进一步走向“能尊重每段经历的事实边界”。它不是把所有未明确写出的技术都删掉，而是把硬事实、软包装、自然承接知识和面试补齐知识分层处理。

## v0.3.7：项目专属表达与重复模板句清理

v0.3.7 处理的是 v0.3.5 之后暴露出的更细一层问题：经历 A 的事实没有写到经历 B，但同一句通用强表达仍然可能被复制到多个经历里。典型例子是多个项目、实习或竞赛中反复出现“围绕文档解析、切块、Embedding、向量检索和回答生成梳理 RAG 应用链路”。这种输出不一定是硬事实幻觉，却会让简历显得模板化，也会让面试官怀疑每段经历是否真的独立。

这一版的核心原则是：

> 事实边界要独立，表达也要尽量项目专属。

主要能力：

- 新增 `project_specificity_guard_service.py`，检查不同项目之间 `intro` / `role` / `details` 的重复句和高度相似句。
- 重复检测覆盖完全相同句子、去掉标点和空格后的高相似文本，以及“文档解析 / 切块 / Embedding / 向量检索 / 回答生成”“Top-K / Retrieval / Chunk / Embedding”等连续技术短语。
- 发现重复模板句后，只保留在最相关的经历中；其他经历优先删除重复句，或基于该经历自身类型和原文生成温和的专属兜底表达。
- 多个 RAG 经历仍然可以同时写 RAG，但必须写出不同侧重点：应用开发、评测测试集、部署链路分别对应不同表达。
- 稳定 fallback 不再把同一条 supported inference wording 机械复制到多个项目。
- DOCX 导出前也执行项目专属表达守卫，历史生成结果重新导出时同样会被清理。

这一版补齐了 v0.3.5 没覆盖到的“表达串通”问题，让系统从“不串事实”进一步走向“不复读模板”。

## v0.3.8：弱经历用户增强策略

v0.3.8 面向校园投放中最常见的一类用户：履历不强，但并非完全没有内容。很多应届生和实习生只有课程大作业、简单个人项目、学生工作、竞赛参与或校级材料。如果系统只做普通润色，这类经历会显得很弱；如果直接写成企业项目、生产系统或获奖经历，又会越过事实边界。

这一版的核心原则是：

> 弱经历也要尽量写出亮点，但每句话都要能被用户解释。

主要能力：

- 新增 `weak_profile_strategy_service.py`，识别输入较短、缺少实习 / 上线 / 用户数 / star / 数据指标、以课程项目 / 大作业 / 小项目 / 学生工作 / 竞赛参与为主的弱履历用户。
- 对课程项目、小项目进行正式化包装，突出需求理解、页面开发、接口联调、材料沉淀、展示答辩和复盘优化。
- 对学生工作和社团经历提炼组织协调、沟通推进、活动执行和材料沉淀能力。
- 对竞赛参与保留方案设计、材料整理、展示答辩和复盘表达，但未提供奖项时不写获奖、排名或证书。
- 对弱经历用户至少补齐 3 条个人优势、每个项目至少 3 条 details，并增加具体追问和面试补强路线。
- DOCX 导出前也执行弱履历策略，历史薄弱结果重新导出时不会过空。

这一版让产品对“最需要简历教练的人”更友好：不是简单指出他们经历薄，而是告诉他们如何把已有材料组织成可投递、可面试承接的成长型画像。

## v0.3.9：简历正文去负面化与实习幻觉防护

v0.3.9 继续打磨弱经历用户场景。真实用户输入里常常会包含“不自信表达”或边界说明，比如“没有实习经历”“没有正式上线”“没有真实用户”“没有获奖”“只是课程作业”。这些信息对边界判断很重要，但如果原样进入正式简历，会直接削弱投递效果。

这一版的核心原则是：

> 负面事实用于边界判断，正向表达用于简历正文。

主要能力：

- 新增 `resume_body_sanitizer_service.py`，清理正式简历正文中的负面、自降和不专业表达。
- “没有实习 / 没有上线 / 没有真实用户 / 没有获奖”等内容不进入 summary 或 projects，而是转入面试准备、追问或边界口径。
- “只是课程作业”“简单小项目”“写了几个页面”“调了一些接口”等表达会被改写为“课程项目”“个人项目实践”“页面开发与交互流程实现”“接口联调与数据流转校验”。
- 增强 `fact_guard_service.py`：原文没有明确实习、公司、工作或岗位线索时，LLM 生成的“实习经历”会被降级为课程项目、个人项目、校园 / 社团经历、竞赛经历或普通项目经历。
- DOCX 导出前也执行正文净化和事实守卫，历史结果重新导出时同样能清理负面正文和实习幻觉。

这一版把 v0.3.8 的弱经历增强补完整：不是假装用户很强，也不是把用户缺点写进简历，而是在事实边界内输出更适合投递的正向表达。

## v0.4.0：Experience ID 事实边界

v0.4.0 将多段经历处理从“生成后修补”升级为“生成前分段、生成中绑定、生成后校验”。v0.3.x 已经通过 fact guard、fallback、正文净化和项目专属表达守卫修复了很多真实问题，但这些能力大多发生在模型输出之后。v0.4.0 的重点是把边界前移：先给每段经历一个内部身份，再要求生成结果绑定身份，最后由后端按身份做审计。

这一版的核心原则是：

> 每段经历独立、真实、可包装、可承接。

主要能力：

- 新增 `experience_identity_service.py`，基于用户原始输入生成 `EXP-001 / EXP-002 / EXP-003` 等内部 experience_id。
- 每段身份会记录经历类型、标题、原文、明确技术词、指标 / 证据词、风险词和可自然承接知识。
- prompt 中注入 experience_id 边界表，要求 `resume_sections.projects` 尽量带上内部字段 `source_experience_id`。
- `result_cleanup_service.py` 保留合法的 `source_experience_id`，但该字段只在后端内部使用，不展示给用户，不进入 DOCX。
- `experience_boundary_guard_service.py` 优先按 `source_experience_id` 做边界校验；缺失时再用名称、经历类型、技术词和证据词回匹配。
- 边界守卫会清理跨经历技术污染、指标污染、上线 / 用户 / star 污染、实习 / 公司 / 奖项污染，并把修复提示放入面试准备。
- `resume_section_fallback_service.py` 和 `stable_generation_fallback_service.py` 支持按 experience_id 逐段生成项目，减少“综合经历项目”兜底。
- 新增 `backend/logs/experience_boundary.jsonl`，记录经历数、项目 source id 缺失数、污染修复次数、修复字段和触发阶段。

这一版进一步压低 fallback 变成“垃圾桶”的风险：fallback 仍然存在，但它必须尊重分段身份；guard 仍然存在，但它不再只能凭顺序猜测项目来源。

## v0.4.1：混合自然语言经历识别

v0.4.1 在 v0.4.0 的 experience_id 事实边界之前增加了语义分段层。用户不再需要严格使用“项目一 / 项目二”或 Markdown 标题；当多段经历连续写在一段自然语言中时，系统会综合标点、新动作、组织与角色、经历类型、主题变化和独立结果计算边界置信度。

主要变化：

- 新增 `semantic_experience_segmentation_service.py`，集中管理自动拆分和谨慎拆分阈值。
- 显式标题优先，语义分段只处理缺少明确结构的输入。
- 个人背景、年级和求职意向不会生成 experience_id，也不会进入项目 details。
- 功能枚举和同一技术链路会保持在原项目中，避免按标点机械拆分。
- 多段 experience_id 已被识别时，fallback 会替换单个“综合经历项目”，按经历逐段生成。
- 边界回匹配没有足够证据时不再按顺序强绑到第一个 experience_id。
- 新增 `backend/logs/experience_segmentation.jsonl`，记录分段数量、置信度、合并次数和低置信度数量，且不记录完整原文。

这一版让系统从“给已经分好的经历加身份”进一步走向“先理解用户到底输入了几段经历，再绑定身份”。

## v0.4.2：项目级内容对账与有效细节回收

真实生成结果 52 暴露了一个新的链路问题：模型已经生成 AI RAG 助手、简历定位与包装网站和 AI Agent 实习三个具体经历，但本地分段因空行被压平而只识别出一个 Experience；fallback 随后从完整原文追加“综合经历项目”，导致数据库和 DOCX 同时出现重复内容。

v0.4.2 的主要变化：

- 保留自然段边界，补充“独立设计并开发”“从零设计”“在某公司实习”等新经历信号，使三段自然语言输入得到三个 experience_id。
- 新增 `resume_project_reconciliation_service.py`，在 generation 保存前和 DOCX 导出前统一对账项目。
- 综合经历删除前逐条回收有效细节：只把能够唯一绑定 experience_id、尚未覆盖且具有技术或证据价值的内容放回具体项目。
- fallback 已有项目时不再重新解析完整 raw_input 生成综合项目，只补充未覆盖的 experience_id。
- 取消按项目数组顺序强绑 source_experience_id；匹配证据不足时保持未绑定并进入日志。
- 项目内容采用最多 18 条、单项目最多 8 条的两页预算，先保证每个项目基本密度，再分配剩余空间。
- 修复 boundary 日志提前返回导致项目数和 source id 缺失数始终为零的问题。
- 新增 `backend/logs/resume_project_reconciliation.jsonl`，跟踪综合项目发现/删除、细节回收/去重和未覆盖 experience_id。

这一版的原则是：事实各归其位，细节应留尽留，重复应删尽删。Fallback 继续负责缺失兜底，但不再通过重复汇总制造表面上的内容丰富。

## v0.4 建议方向

v0.4 建议继续围绕“输出质量中枢”迭代。

优先方向：

- Experience ID 继续下沉：让 Claim、面试准备、知识清单也能绑定 `source_experience_id`。
- 分阶段生成：先生成经历结构，再生成包装文本，再生成 Claim 和面试准备，减少一次性大 JSON 失控。
- 输出质量评分：检查结果是否具体、岗位匹配、可承接、少空泛。
- 反空泛规则：减少“提升用户体验”“负责相关工作”等无效表达。
- 岗位化生成策略：同一段经历针对 AI Agent、后端、前端、数据分析等岗位突出不同重点。
- 真实案例回归集：把真实用户 case 固化为测试样例，每次 prompt 或模型配置变更后跑回归。
- DOCX 版式优化：继续提升正式简历文件的投递质感。
