# v0.4.x 阶段复盘

## 阶段主题

v0.4.x 将系统从依赖生成后文案修补，推进为“生成前建立身份与事实来源、生成中绑定来源、生成后验证覆盖和边界”的质量工程体系。

## 真实用户暴露的问题

- 长输入将个人项目错误路由到实习经历。
- 项目 A 的 RAG、指标或产品内容进入项目 B。
- 输入内容充实，但通用包装句挤占了高价值事实。
- 多条详情用不同措辞重复同一件事。
- 求职教练话术、用户指令和内部字段进入正式简历。
- DOCX 包含面试准备或缺少正式投递所需标题。

## 从关键词到关系语义

“实习”并不总表示作者有实习。产品可能面向实习生，也可能提供实习岗位推荐。v0.4.x 将类型判断改为作者、关系动作和经历对象联合评分，并记录正向证据、排除语境、候选类型和分差。

## 从项目边界到事实 Provenance

`experience_id` 解决项目归属，Fact Ledger 进一步把每段经历拆成 `fact_id`。Coverage Guard 检查高价值事实是否进入正文，Dedup 合并重复表达时保留事实 ID。系统由“项目是否存在”升级为“具体事实是否被正确承载”。

## Dedup Precision / Recall

去重过弱会留下模板感，去重过强会吞掉 RAG 实现、评测、Citation、部署和数据隔离等独立事实。v0.4.10 使用包含关系、source fact IDs、实验动作簇和高置信语义相似度，只合并同一事实的复述，并允许每段经历保留 6-8 条独立高价值内容。

## 为什么需要管线治理

Guard 数量增加后，问题不再是单个服务是否正确，而是执行顺序是否保持不变量。Fact Coverage 会恢复正文，因此需要边界和去重复检；语言和完整性服务会改写正文，因此需要最终事实与污染复检。v0.4.11 将这些关系写入正式管线文档，并用匿名真实案例固定行为。

## Fallback 不是垃圾桶

Fallback 可以避免用户拿到空白 DOCX，但不能掩盖 LLM 退化。系统记录 Stable Fallback、Resume Section Fallback 的调用阶段、触发原因和触发率，并在质量报告中设置观察阈值。

## 当前技术债务

- 生成与 DOCX 二次检查仍有较多相似调用，未来适合抽象为带阶段配置的 Pipeline Runner。
- 当前质量指标主要来自规则日志，缺少统一的 generation correlation id。
- 事实覆盖衡量“是否出现”，尚未完整衡量表达质量和岗位相关性。
- 回归集使用确定性链路，真实模型需要离线评测集与版本对比。
- SQLite 与 JSONL 足够支撑内测，但更大规模需要集中日志和指标存储。

## v0.5.0 建议

建立 Output Quality Eval：事实正确率、经历覆盖率、跨经历污染率、重复率、包装增益、专业度和投递就绪度。每次更换模型、Prompt 或 Guard 顺序时，用同一批案例做可比较评测，而不是继续依靠主观抽查。

## 可用于项目复盘的表达

设计并迭代面向技术求职场景的结构化 LLM 生成链路，引入 Experience ID 与 Fact Ledger 跟踪多段经历的事实来源，通过 Fact Coverage、Boundary Guard、关系语义类型解析和高价值事实保留式去重，解决长输入下的经历串用、事实遗漏、类型误判和重复表达问题；结合 Stable Fallback、DOCX 投递检查及 JSONL 质量指标，使模型异常对用户透明、对开发者可观测。
