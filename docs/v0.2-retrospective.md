# v0.2.x 复盘：稳定性与可观测性收口

## 阶段主题

v0.2.x 的阶段主题是：从“能跑通流程”推进到“真实用户使用时稳定可交付”。

这一阶段没有新增登录、支付、PDF、上传简历等大功能，而是围绕真实使用中暴露的问题，补齐 LLM 产品最容易被忽略的工程安全层：

- 用户可见文本是否像正式产品。
- 页面展示和 DOCX 交付是否一致。
- 结构化输出合法但业务不可用时，系统是否能兜底。
- fallback 触发后，开发者是否能感知上游模型退化。

## 真实用户暴露的问题

真实用户测试中出现了一个很有价值的问题：

页面上的包装结果是有内容的，但导出的 DOCX 简历主体为空白。

排查后发现，LLM 返回的 JSON 在格式上完全合法，`recommended_version` 中也有完整内容，但 `resume_sections.summary`、`resume_sections.skills`、`resume_sections.projects`、`resume_sections.interview_preparation` 是空数组。

前端展示读取的是 `recommended_version`，所以用户看到页面正常；DOCX 生成读取的是 `resume_sections`，所以文件主体为空。

这不是输入质量问题，而是 LLM 结构化输出在业务语义上的不完整。

## 核心教训

> 结构合法不等于业务可用。

此前系统已经具备：

- JSON 修复，解决格式不合法。
- Pydantic 校验，解决字段缺失和类型错误。
- 结果清洗，解决内部字段泄露和展示污染。

但这次问题绕过了这些保护，因为空数组在 schema 上是合法的。它说明 LLM 应用不能只检查“是否能解析”和“字段是否存在”，还要检查“这个结果能不能交付给用户”。

## Resume Section Fallback 设计

v0.2.2 新增 Resume Section Fallback，用来处理 `resume_sections` 过空的问题。

设计原则：

- 保留已有非空结构，不覆盖正常结果。
- 优先从 `recommended_version` 解析。
- 其次从 `bold_version`、`normal_version` 解析。
- 最后从 `confirmed_facts`、`claims`、`knowledge_checklist`、`interview_plan` 组合兜底。
- 如果项目结构无法稳定解析，至少生成一个“综合经历项目”，避免 DOCX 主体空白。
- 不编造用户未提供的新事实，只做拆分、整理、合并和结构化。

Fallback 在两个位置生效：

- 生成结果保存前：保护新数据。
- DOCX 导出前：保护历史空结构数据。

## Fallback 是安全网，不是垃圾桶

v0.2.3 进一步补齐 fallback 可观测性。

如果 fallback 静默吞掉大量上游问题，用户暂时不会感知，但开发者会失明。模型升级、prompt 退化或结构化输出质量下降时，系统表面正常，实际质量可能已经变差。

因此 fallback 日志记录：

- 是否触发 fallback。
- 触发阶段：`generation` 或 `docx_export`。
- 补全了哪些 section。
- 触发原因，例如 `structured_resume_empty`、`projects_empty`。
- 来源字段，例如 `recommended_version`、`knowledge_checklist`。
- 对应的 `generation_result_id`。

analytics 报告会汇总 fallback 调用次数、触发次数、触发率、section 分布、reason 分布和来源字段分布。

这让系统做到：

> 用户不能感知故障，但开发者必须能感知故障。

## v0.2.x 对 v0.3.0 的启发

v0.2.x 说明项目已经进入真实产品阶段。下一阶段不应继续只修稳定性，而应该提升生成质量。

v0.3.0 可以围绕以下方向展开：

- Prompt 分层：把经历解析、岗位定位、包装生成、Claim 检查、面试准备和 resume_sections 生成拆开。
- 输出质量评分：判断生成结果是否具体、岗位匹配、可承接、少空泛。
- 反空泛规则：减少“提升用户体验”“负责相关工作”等弱表达。
- 岗位化生成策略：不同岗位突出不同能力重点。
- 真实案例回归集：把真实用户问题固化为测试样例，避免后续迭代回退。

## 可写进项目复盘的总结

在真实用户测试中发现，LLM 返回结果虽然满足 JSON schema，但存在业务语义不完整问题：页面推荐版本有内容，而正式简历结构字段为空，导致 DOCX 导出主体空白。为此设计并实现 Resume Section Fallback，在生成保存前和 DOCX 导出前对结构化简历字段进行业务完整性检查，并从推荐版本、Claim、知识清单和面试计划中补全个人优势、技能栈、项目经历和面试准备。同时增加 fallback 可观测性，将触发阶段、补全 section、触发原因和来源字段写入日志并汇总到 analytics 报告，避免 fallback 静默掩盖上游 LLM 输出退化。
